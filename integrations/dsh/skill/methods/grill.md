# Helix · 压力测试（Grill）

> 触发：`helix grill` / "审问这个计划" / "盘问我" / 对既有计划、设计、Seed 做压测。
> 字面含义的"烤"（烹饪）不触发。

立场：**试图推翻**，不是帮忙润色。用反对者人格（`methods/personas.md` #5）主持，一次只问一个问题。

## 审问顺序（按杀伤力排序）

1. **存在性**："不做这个会怎样？现有的东西为什么不够？"——最便宜的胜利是发现根本不用做。
2. **最脆弱假设**："整个方案押在哪个假设上？这个假设被验证过吗、怎么验的？"
3. **被放弃的方案**："放弃了什么替代方案、依据是什么？是真比较过还是先入为主？"
4. **爆炸半径**："失败时炸到谁？回滚路径是什么、演练过吗？"
5. **本体拷问**："方案里每个关键名词，两个人的理解一致吗？"（状态、生命周期、归属）
6. **验收拷问**："每条成功标准，写得出验证动作吗？谁来跑、看什么输出？"
7. **范围拷问**："哪些是这次坚决不做的？说不出 Non-goals 的计划必然蔓延。"

## 规则

- 一次一个问题；有选项卡片就用卡片（2–4 个具体选项 + 推荐项）。
- 每个回答追问到**证据或承认是假设**为止，但同一点最多追两层，不无限缠斗。
- 被确认的假设记入 Seed 的 Assumptions；被推翻的点当场改计划，不留"回头再说"。
- 结束条件：高杀伤力问题（1–4）全部过堂，或用户喊停。
- 输出：一段"压测结论"——存活的方案 + 修正点清单 + 仍未消除的风险。

## 文档级压测（对长规格/长计划）

对成文规格做整体评审时，派一个独立子代理（评估者人格 #4），提示词要点：

```text
你评审这份规格/计划文档，立场是找缺陷不是夸它。按顺序检查：
1. 完整性：AC 是否可验证、边界条件是否声明、失败路径是否有交代；
2. 一致性：术语前后同义吗？与项目现有契约冲突吗（对照给出的基线引用）；
3. 可执行性：一个不了解上下文的实现者按它能动手吗？缺哪些精确文件路径/接口签名；
4. 风险：最可能返工的三个点。
结论先行，逐条给位置。没有发现就明说，并指出你没覆盖的面。
```
