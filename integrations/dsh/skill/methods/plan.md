# Helix · 计划的编写与执行（Plan）

> 触发：`helix plan`；或 L2 任务 Seed 已结晶且满足其一：任务跨会话、需要用户审批后分批执行、或要派多个实现子代理。
> 单会话一口气能做完的 L2 不写计划文档——Seed 的 AC 清单就是计划（文件必要性门）。

## 编写计划

计划是给"零上下文实现者"看的：假设读者不了解项目、没有品味、不会脑补。每个任务写到**照做就能对**：

```markdown
# Plan: <任务名>（对应 seed-N）
## 批次 1: <名字>          ← 一个批次 = 一个可验证的检查点
### Task 1.1: <一句话>
- 文件: <精确路径>
- 改动: <做什么，含关键接口签名/数据结构>
- 验证: <跑什么命令，期望看到什么输出>
- 依赖: <前置任务号，或"无">
### Task 1.2: ...
## 批次 2: ...
```

切分法则（源自 Superpowers，按证据校准）：

- 单个 Task 以**一次专注编辑 + 一次验证**为度（约 2–15 分钟人类工时）；再大就拆。
- 每个 Task 必须有独立验证动作——写不出验证的 Task 说明还没想清楚，回 clarify。
- 批次边界 = 系统处于可运行状态的点。任何批次结束都能安全停下。
- 依赖显式声明；无依赖的 Task 标记出来，它们是并行派发的候选。

落盘：`.helix/plan.md`（跨会话/需审批时）。计划从 Seed 推导，**不得与 Seed 冲突**；冲突说明 Seed 要 reseed，不是计划打补丁。

## 执行计划

- **按批次执行**：批次内按依赖顺序做 Task；每个 Task 完成即跑它声明的验证，勾掉；批次结束跑 Gate 1 机械门全量检查，追加 journal。
- **检查点**：需要用户审批的计划，批次结束停下来给差异摘要，批准后进下一批；自主模式连续执行但保留每批次的 journal 记录。
- **偏航处理**：执行中发现计划错了（文件不在、接口不同、方案不通）——停止该批次，修订计划并在 journal 记一行"计划修订: 原样→现样+原因"；连续两个 Task 都偏航说明计划质量有问题，回 grill 压测一遍再继续。
- **多实现者并行**：无依赖 Task 可派发实现子代理（提示词模板见 `methods/subagents.md`），坐标员（你）不同时亲自写码——要么全派发要么全亲写，混着写容易冲突。
- 全部批次完成 → 走 `methods/verify.md` 三级门，计划完成不等于任务完成。
