# Helix · TDD 与测试反模式

> 触发：TDD 路由命中（用户显式要求 strict，或 AC 可测试化且项目有测试设施并已向用户建议）。
> Helix 与 Superpowers 的分歧：TDD 是**按风险路由的纪律**，不是无差别强制——探索性/不可自动化的工作不硬套。但一旦进入 strict 模式，规则与 Superpowers 同样硬。

## Strict 模式协议（红 → 绿 → 重构）

1. **红**：为下一个行为写一个失败测试，**亲眼看它以预期理由失败**——没见过红的测试不可信（可能测了个寂寞）。
2. **绿**：写让它通过的最小实现，不顺手实现下一个行为。
3. **重构**：绿灯保护下清理重复与命名；重构期间不加新行为。
4. 一次一个行为，循环。每个循环结束是一个天然提交点。

Strict 模式红线：**实现先于测试的代码要重写**——先写了实现再补测试，测试会不自觉地顺着实现写（只验证"它做了它做的事"）。发现自己先写了实现：留下接口、删掉实现体、先写测试再恢复。

## 测试反模式（任何模式下都禁止，源自 Aegis/Superpowers 铁律）

1. **测 mock 的行为**：断言"mock 存在/被调用了"而不是断言真实产出。问自己："这条断言在测组件还是在测我自己写的 mock？"
2. **给生产类加测试专用方法**：`destroy()`/`reset()` 只有测试在用 → 测试设施放测试侧，不污染生产 API。
3. **不理解依赖就 mock**：mock 掉的东西正是被测逻辑的一部分 → 测试永远绿但什么都没验。
4. **为过而弱化**：放宽断言、扩大容差、skip 失败用例、加 retry 掩盖 flaky——测试挂了只有两个合法出路：修实现，或证明测试错了（带依据）。
5. **睡眠等待**：`sleep(2000)` 等异步结果 → 换成条件等待（轮询某个可观测条件直到成立或超时），否则慢且 flaky。
6. **测试互相污染**：共享可变状态导致单跑绿、连跑红 → 用二分法找污染者（跑一半用例定位区间，递归缩小），修隔离而不是调顺序。

## 覆盖的诚实度

- 测试覆盖了什么、没覆盖什么，如实写进证据收据的"覆盖范围/未覆盖"栏。
- 新增行为没有对应测试时，收据置信最高 B，并在"下一个最有价值的验证"里点名缺的测试。
