# Helix · Git 纪律（worktree 与分支收尾）

> 触发：并行改动需要隔离、脏工作区挡路、分支/PR 生命周期、任务收尾提交。

## 何时建 worktree / 分支

- **默认不建**。复杂度高、要用子代理、要写计划——这些都**不是**建分支/worktree 的理由（跟随 Aegis 纪律，防仪式性分支）。
- 建的正当理由：用户要求 PR 流程；多条改动线并行且互相干扰；工作区有用户未提交的状态不能动；实验性改动需要一键丢弃。
- worktree 建在项目目录外的固定位置（如 `../<repo>-wt/<name>`），建完先跑一次构建/测试确认基线绿，再动工。

## 任务收尾（Task Closeout）

任务完成（三级门已过）后的 git 动作，坐标员亲自执行：

1. `git status --short` 全量看一遍：**逐个认领**本任务产生的文件；不认识的文件不许进提交（可能是用户的或工具的）。
2. 精确暂存任务所属路径，**禁止 `git add -A`/`git add .`**。
3. 提交信息：一句话"做了什么+为什么"，正文可引用 Seed/AC 编号。机械性改动的提交信息就是全部文档（文件必要性门）。
4. 提交后读回：`git log -1 --stat` 核对内容与预期一致；工作区残余的非任务文件如实报告，不清理不隐瞒。
5. hook 失败 = 阻塞：修 hook 报的问题，**不许 `--no-verify` 绕过**。

## 分支收尾（用户走 PR 流程时）

- 合并前置：目标分支最新、全量测试绿、评审 critical 清零。
- 收尾四选项交用户裁决：合并 / 发 PR / 保留分支待续 / 丢弃。不替用户决定合并。
- 收尾后清理:被合并的分支与 worktree 删除；保留的写明保留原因与预期寿命（反熵：无主分支是幽灵代码的温床）。

## 破坏性操作红线

`push --force`、`reset --hard`、删分支、改历史：需要用户**针对性授权**（说清对象与后果），笼统的"你看着办"不算。执行前把将被丢弃的内容列出来。
