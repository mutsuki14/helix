# Helix · 代码评审（请求与接收）

> 触发：`helix review`、合并前评审、Gate 3 共识门的评审员派发、收到评审反馈要处理。

## 请求评审（派发独立评审员）

时机：每个实现切片完成后、合并高风险工作前。评审员必须**独立**（没参与实现的子代理），给它 diff 范围而不是你的自评：

```text
你评审这次改动的生产就绪度。立场：找缺陷，不是背书。

## 范围
基线: <BASE_SHA>   头: <HEAD_SHA 或 working-tree>
用 git diff --stat 和 git diff 查看；只读，不修改、不暂存、不提交。

## 对照物
<任务/Seed 的 AC 原文贴入；没有对照物本身就是一个 major 发现>

## 检查序（结论先行，发现优先，不写综述）
1. 正确性: 边界/空值/异常路径/并发/资源泄漏——给出能出错的具体输入或时序；
2. 契约: 对外接口/schema/事件的变更是否声明、消费方是否处理；
3. 归属: 修在 owner 还是在调用方打补丁掩盖源头问题；
4. 复杂度: 每个新增兜底/分支/适配层的存在理由；无理由的点名删除；
5. 测试: 新行为有测试吗？反模式（测 mock/弱断言/睡眠/污染）扫一遍；
6. 安全: 注入面、权限检查、敏感数据落日志。

每条发现: 位置(文件:行) + 严重度 + 一句修法建议。
severity: critical(阻塞合并) / major(合并前应修) / minor(可记账后续)。
没有发现就明说，并列出你未覆盖的面与残余风险。
```

## 接收评审（处理反馈的纪律）

源自 Aegis receiving-code-review，核心：**对证据负责，不对权威低头，也不对自尊护短**。

1. 逐条分类，禁止笼统"好的都改"：
   - **接受**：反馈指出的问题能用证据确认 → 修，修完跑该点的验证；
   - **反驳**：反馈错了 → 拿出证据（复现/文件行/规范原文）说明，不是"我觉得没问题"；
   - **存疑**：无法快速判定 → 标记出来交用户/提出者裁决，不默默吞掉。
2. critical 未清零不进收据；major 未修的写进收据"残余风险"并给理由。
3. 评审建议引发的**范围外重构冲动** → 记 `later`，不在本任务顺手做。
4. 修复后的再评审只看增量：把"上轮发现→处置"清单发回，不重开全面评审。
5. 多个评审员意见冲突时回到证据裁决；证据不可得就如实上报分歧，不和稀泥。
