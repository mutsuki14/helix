# Helix · 澄清与结晶（Clarify → Seed）

> 前置：已按 `SKILL.md` 总路由分级为 L2，或用户显式要求 `helix seed` / `helix grill`。
> L1 任务只用本手册末尾的"迷你 Seed"，不走完整流程。

核心信念（源自 Ouroboros）：**AI 编码的失败大多发生在输入端**——人没说清楚，而不是模型做不到。所以先把钱花在问题上，再花在答案上。

## 第一步：苏格拉底访谈

目的：从"想要什么"一路问到"这个东西究竟是什么"。

规则：

- **一次只问一个决策问题**；宿主支持选项卡片（AskUserQuestion 之类）就优先用卡片，给 2–4 个具体选项并标注推荐项。
- 只问推不出来的。能从任务描述、代码库现状直接推断的不要问——先自己查（读 README、现有实现、同类先例），查完还含糊才问。
- 问题分三层，按需深入：
  1. **目标层**："做成什么样算成功？失败的版本长什么样？"
  2. **约束层**："什么不能动？（现有 API、数据格式、性能、依赖）有没有截止边界？"
  3. **本体层**（Ouroboros 特色）："这个概念到底是什么？"——追实体的身份与生命周期。例："任务能删除还是只能归档？""一个用户能属于几个组织？""状态回退合法吗？"本体层问题最能提前消灭返工。
- 用户不可用（自主模式）时：不空转等待。用代码库证据+行业惯例做出**显式假设**，把每条假设写进 Seed 的 Assumptions 区，标注"未经确认"。

`helix grill` 模式（压力测试既有计划/设计）：立场换成**试图推翻**，完整协议读 `methods/grill.md`。
访谈/评审人格的现成提示词见 `methods/personas.md`（苏格拉底访谈者、本体论者、规格架构师）。

## 第二步：歧义评分门

访谈到什么时候为止？用量表算，不靠感觉。这是 Ouroboros 歧义门的零配置移植：**由你（Agent）自评，但每个分数必须写出依据**，不许拍脑袋。

对以下维度各给一个清晰度分 `clarity ∈ [0, 1]`：

| 维度 | 权重（绿地） | 权重（棕地） | clarity = 1.0 的标准 |
|---|---|---|---|
| 目标 Goal | 0.40 | 0.34 | 成功/失败的分界能用一句话说清，无多义词 |
| 约束 Constraints | 0.30 | 0.26 | 不能动的东西全部点名；无"大概不能改"的灰区 |
| 成功标准 Success criteria | 0.30 | 0.26 | 每条验收都写得出验证动作（跑什么、看什么） |
| 项目上下文 Context（仅棕地） | — | 0.14 | 涉及的现有模块、契约、惯例已读过并理解 |

```
Ambiguity = 1 − Σ(clarity_i × weight_i)
```

各维依据写好后，用随包脚本做确定性计算（不要心算）：
`node scripts/gate.mjs '{ mode: "ambiguity", goal: 0.9, constraints: 0.7, success: 0.8, brownfield: true, context: 0.85 }'`（脚本在本技能目录下；无 node 时按上方公式手算，并把每一步算式写在回复里）

**门槛：Ambiguity ≤ 0.2 才可结晶 Seed。** 超过就回去继续访谈/查证，优先补加权贡献最低的维度。

自评纪律：每个 clarity 分数旁边写一行依据（如"约束 0.6：用户没说旧 API 是否保留，我按保留假设"）。写不出依据的分数一律按 0.5 计。

**棕地专项**：context 维度自评 < 0.8 时，不要硬着头皮给分——先做代码库考古把清晰度用证据抬上去：`methods/brownfield.md`（地形/契约/归属/术语四步），考古完成后重评。

## 第三步：结晶 Seed（不可变规格）

过门后把共识结晶成 Seed。格式：

```markdown
# Seed: <任务名>            （版本: seed-N，日期）
## Goal          一句话目标 + 成功的样子
## Non-goals     明确不做的事（防范围蔓延的锚）
## Constraints   不能动的契约/依赖/性能/风格约束
## Acceptance Criteria
- [ ] AC1: <可验证陈述> — 验证方式: <跑什么命令 / 检查什么输出>
- [ ] AC2: ...
## Ontology      关键实体、状态集合、生命周期规则（本体层访谈的结论）
## Assumptions   未经用户确认的显式假设（自主模式下必填）
## Stop conditions
done | blocked | needs-verification | scope-exceeded 各自的判定
## Ambiguity     最终得分与各维依据
```

**不可变规则**（Ouroboros 的 Seed 锁 + Aegis 的漂移规则）：

- 执行期间**不修改 Seed**。发现需求真变了 → 显式 **reseed**：旧 Seed 归档（`seed-1.md`），新 Seed 里写明"与上版差异、变更原因、受影响的已完成工作"。禁止静默改口。
- 执行中冒出的范围外好主意 → 记入 journal 的 `later` 区，不改 Seed、不顺手做。
- Seed 落盘与否遵守 `core` 的文件必要性门：跨会话/多圈/需审批才写 `.helix/seed.md`，否则放在回复里即可。

## L1 迷你 Seed

L1 任务只需 3 行，写在回复里，不落盘、不算歧义分：

```text
目标: <一句话>
验收: <怎么验证算成>
边界: <不动什么>
```

写完迷你 Seed 直接进入执行：读 `methods/build.md`。
L2 同样：Seed 结晶完成后进入 `build`。
