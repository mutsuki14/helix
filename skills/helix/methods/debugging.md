# Helix · 深度调试（Debugging Deep-Dive）

> 触发：`methods/build.md` 的五步调试不够用——复现困难、根因链条长、flaky、或两次修复失败。

## 根因追溯术

- **沿数据流向上游问**："这个错误值从哪来？"逐层追：出错点 → 赋值点 → 输入点 → 源头。每层记录证据（变量值/日志行），直到找到**第一个违反预期的地方**——那里才是根因，之前都是症状。
- **二分定位**：链条太长时二分——对输入二分（最小复现输入）、对版本二分（git bisect，用可复现的判定脚本）、对代码路径二分（中点插观测）。
- **区分三种"修好了"**：真根因修复 / 掩盖症状（在出错点吞异常）/ 碰巧扰动（改了时序让它暂时不炸）。后两种在收据里如实标注，不许冒充第一种。

## Flaky 与异步

- 间歇失败 ≈ 时序或隔离问题，两大来源：
  - **睡眠等待**：把 `sleep` 换成条件轮询（等到可观测条件成立或超时报错，超时信息里带"等什么没等到"）。
  - **测试污染**：单跑绿、连跑红 → 二分用例集合找污染者，修共享状态隔离。
- 复现率低时先提高观测密度（在关键路径加结构化日志），拿到一次带完整现场的失败再分析，不做无现场推理。

## 纵深防御修复

根因修复后问一层："同类错误为什么能走到这么深才炸？"在**合适的最上游**加一道防线（输入校验/类型收紧/断言），一道就够——层层设防每处 try/catch 是反模式，会把下一个 bug 的现场吞掉。

## 二击规则（源自 Ouroboros 停滞思想）

同一 bug 两次修复尝试失败 → 停止第三次尝试，强制切换：

1. 写下两次尝试各自的假设、改动、失败方式（这就是 loop 模式的失败分析）；
2. 用研究者人格问：我缺的是不是信息？（读依赖源码/文档/issue，而不是继续猜）
3. 用反对者人格问：我对"正常行为"的理解本身对吗？（验证被我当作公理的前提）
4. 仍无路 → `helix unstuck` 完整五视角（`methods/evolve.md`）。

## 修复的验证

- 原复现步骤转绿只是及格线；还要：相邻场景回归 + 如果是并发/时序 bug，重复运行 N 次（flaky 修复跑 20 次全绿才算数）。
- 修复涉及的每个新增分支/兜底：给出存在理由，否则删掉（反熵）。
