# Helix · 棕地考古（Brownfield Exploration）

> 触发：L2 任务落在已有代码库上，且歧义门的 context 维度自评 < 0.8；或用户要求"先摸清这个项目"。
> 目的：把 context 维度的清晰度用证据抬上去，而不是靠自信。

## 考古四步（自顶向下，每步有产出）

1. **地形**：README / 构建配置 / 目录一层 → 得出"这是什么、怎么跑起来、代码分几块"。跑一次构建/测试，记录基线是绿是红——**红基线必须先声明**，否则你的改动会背锅。
2. **契约**：与任务相关的接口、类型、schema、事件、配置格式 → 读实际定义。产出**契约清单**：叫什么、定义在哪、谁消费。
3. **归属**：任务要动的每个行为，现在的 owner 文件/模块是谁 → `grep`/结构搜索定位，看 2–3 个同类改动的历史先例（git log 该文件）。产出**归属表**：行为 → owner → 改动落点。
4. **术语**：项目里含义特殊、有歧义或已改名的领域词 → 产出**术语表**（下方格式）。只收"会引起误解的词"，不做全量词典。

范围大时派只读探索子代理分头做 1–3，回收结论不回收文件堆；第 4 步自己做（术语歧义要人的判断）。

## 术语表格式（存疑词才入表）

```text
术语: <词>
含义: <本项目内的精确含义>
别名/旧名: <代码里还叫什么>
陷阱: <容易被误解成什么>
出处: <定义或典型用法的文件:行>
```

跨会话的 L2 任务把术语表并入 `.helix/seed.md` 的 Ontology 区；一次性任务放在回复里即可。

## 考古纪律

- **带着任务考古**，不做漫游式通读：每一步只挖与 Seed 相关的面。
- 先例优先于偏好：项目惯例与你的最佳实践冲突时，默认从项目惯例，想改惯例走 ADR。
- 遗留怪异代码：先假设它有历史原因（Chesterton 栅栏），git log / blame 查动机，查不到再按可疑处理。
- 考古结论全部是**证据候选**：写进 Seed 前，关键结论要能给出文件:行的出处。
- 考古完成后重跑歧义门（context 维度重新自评），过门才结晶 Seed。
